# ADR 0013: privileged executors trust core within their ceilings

Status: accepted by the owner, 2026-11-20, as the documented model for plan row PR-30 (`docs/plans/2026-11-19-production-readiness-plan.md`). This records the model and what the code enforces today. The executor-side rate limit and action log that PR-30 also asks for are not implemented.

Context. Core (`limeos-core`) is unprivileged and network-facing. It authenticates administrators, checks grants and approval tokens, and dispatches work to separate executor processes over Unix sockets. Each executor holds a privilege that core lacks: Docker group membership, or root. The architecture already says core is a trusted component that, if compromised, "could misuse operations allowed by that ceiling and fabricate its own internal approvals" (`docs/plans/2026-10-04-rust-rewrite-architecture.md:146`). ADR 0003 says the executor "trusts core within the root-owned ceiling and does not verify approvals" (`docs/adr/0003-p03-durable-container-operations.md:21`). The production-readiness plan asked the owner to accept that model or to require an independent approval path before any storage effect ships (`docs/plans/2026-11-19-production-readiness-plan.md:137`). The owner accepted the model.

Decision. An executor performs any well-formed request from core's UID that its role's root-owned ceiling allows. It does not re-authorize the administrator. No approval token, session or user identity reaches an executor. Core checks the approval when it queues a job (`crates/persistence/src/plans.rs:233`). It re-checks the grant and the plan's expiry right before dispatch (`bins/core/src/operations.rs:534-551`). It then sends only the action ID, the plan digest and the plan (`bins/core/src/operations.rs:565-576`). The executor accepts the plan if four checks pass. The plan hashes to the digest it carries (`crates/executor-container/src/lib.rs:456-460`). Its lifetime is at most 300 seconds and has not expired (`crates/domain/src/operations.rs:7`, `:174-191`). A fresh Engine inspection equals the plan's expected snapshot (`crates/executor-container/src/lib.rs:485-488`). The target is within the ceiling (`crates/executor-protocol/src/lib.rs:656-681`, rechecked in `crates/executor-container/src/lib.rs:57-79`). The plan's `principal` and `grant_revision` are checked for format only (`crates/domain/src/operations.rs:176-179`). Core can read the same fresh inspection through the `Inspect` request (`crates/executor-protocol/src/lib.rs:506-514`). So a core that is compromised can mint a plan the executor accepts, whenever it wants.

What bounds a compromised core today.

- Socket access. Each socket is created mode 0660 (`bins/executor/src/main.rs:269-270`, `bins/executor/src/storage_targets.rs:38-39`, `bins/executor/src/storage_runtime.rs:55-56`). It lives in a runtime directory of mode 0750, group `limeos-container-access` or `limeos-host-access` (`packaging/systemd/limeos-containerd.service`, `packaging/systemd/limeos-storaged.service`). Core holds both groups (`packaging/systemd/limeos-core.service`).
- Peer credentials. Every role compares the SO_PEERCRED UID with the ceiling's `core_uid` before it reads a frame (`bins/executor/src/main.rs:327-333`, `bins/executor/src/storage_targets.rs:57-63`, `bins/executor/src/storage_runtime.rs:67-71`). The comparison repeats in `Ceiling::validate` and in every authorize call (`crates/executor-protocol/src/lib.rs:465-468`, `:643`, `:664`). Frames are capped at 64 KiB (`crates/contracts/src/lib.rs:16`, `:302`).
- Role split. The role is fixed by argv at start. The host and storage-reader roles refuse any ceiling that grants writes or logs (`bins/executor/src/main.rs:204-225`, `crates/executor-protocol/src/lib.rs:452-460`). The storage effect roles insist on their fixed policy path, socket, binary and root (`bins/executor/src/storage_targets.rs:14-23`, `bins/executor/src/storage_runtime.rs:27-37`).
- Ceilings and what they are keyed on. Container ceilings list full 64-hex Engine container IDs, not names (`crates/domain/src/operations.rs:122-127`, `crates/executor-protocol/src/lib.rs:442-446`, `:676`). Stack ceilings list Compose project names, and every member must also be a listed container ID (`crates/executor-protocol/src/lib.rs:637-655`). Storage ceilings list exact filesystem UUID and mountpoint pairs under `/mnt/`, and mounts also name a target ID (`crates/executor-protocol/src/lib.rs:296-437`). A ceiling must be root-owned and not group- or world-writable (`bins/executor/src/main.rs:187-190`; the storage effect roles use `read_protected_json`, `crates/executor-storage/src/targets.rs:44`). The package installs read-only defaults: the container ceiling grants no effect and lists no container (`packaging/debian/postinst:55-73`).
- One effect at a time. Container effects share one receipt-store lock taken with `try_lock` (`bins/executor/src/main.rs:443-445`). A unique index refuses a second action on a resource while one is prepared, accepted or unknown (`crates/executor-container/src/lib.rs:243`).
- systemd sandboxing, per unit (see the role list below).
- Receipts in executor-owned stores. Core cannot open them. The container store directory is 0700 and owned by `limeos-containerd` (`packaging/debian/postinst:51`). The store refuses any other owner or mode (`crates/executor-container/src/lib.rs:173-200`). A replayed action ID returns its stored receipt instead of running again (ADR 0003).
- Log redaction in the executor. Container logs are redacted before they leave the container executor, so core receives redacted text (`crates/executor-container/src/logs.rs:1-2`).

What a compromised core can and cannot do, per role.

The container executor (`limeos-containerd`) is enabled by default (`packaging/debian/postinst:82`). It runs as `limeos-containerd` with the `docker` group, no capabilities, `AF_UNIX` only and `ProtectSystem=strict` (`packaging/systemd/limeos-containerd.service`).

- With the default ceiling, core can read only. It can observe every container (`Observe`), inspect any container by ID (`Inspect`), list the members of any Compose project (`InspectStack`) and read the Engine storage inventory (`ContainerStorageInventory`). The single `allow_container_read` flag gates all four, and they are not limited to the managed list (`crates/executor-protocol/src/lib.rs:480-514`, `:549-555`). Logs require `allow_container_logs` and a listed container (`crates/executor-protocol/src/lib.rs:526-540`).
- Once the operator grants `allow_restart`, `allow_start`, `allow_stop` or `allow_stack`, core can perform the granted action on any listed container or stack, as often as it likes. It can verify each action itself with a fresh inspection (`crates/executor-container/src/lib.rs:538-583`) and send the next one. A restart loop, or keeping every listed container stopped, is within the ceiling.
- It can also write receipt rows through requests. A lookup with `close_if_absent` writes a closure for any action ID (`crates/executor-container/src/closure.rs:229`). `ResolveAction` marks a stuck action resolved and frees its lock (`crates/executor-container/src/resolution.rs:123-151`). It records whatever `resolved_by` ID core supplies, behind evidence core can compute. Retention keeps only 1024 container and 256 stack receipts (`crates/executor-container/src/retention.rs:81-83`). Churning rows prunes older ones.
- It cannot act on an unlisted container or project. It cannot create, remove, exec, pull or change images or networks: the protocol has no such request (`crates/executor-protocol/src/lib.rs:43-211`), and the Engine trait reaches only fixed endpoints (`crates/executor-container/src/lib.rs:110-127`, `crates/executor-container/src/docker.rs`). It cannot reach the Docker socket itself: the package refuses Docker membership for every other service account (`packaging/debian/postinst:13-15`). It cannot change a ceiling, which is root-owned.

The host executor (`limeos-storaged`) is enabled by default. It runs as `limeos-storaged` with no capabilities, `PrivateNetwork`, `ProtectSystem=strict` and `~@privileged` (`packaging/systemd/limeos-storaged.service`). Its ceiling grants health and host reads (`packaging/debian/postinst:62`). Core can read host metrics, ask for a more active collection cadence (`bins/executor/src/main.rs:398-415`) and ask for health. Every other request is refused (`bins/executor/src/main.rs:649`).

The storage reader (`limeos-storage-reader`) runs as root without a mount namespace. Its unit has no `[Install]` section, and the package does not enable it (`packaging/systemd/limeos-storage-reader.service`, `packaging/debian/postinst:82`). Its ceiling must be read-only (`bins/executor/src/main.rs:204-218`). Core can trigger the root reads behind `StorageInventory`, `StackInventory` and the nonce-bound `ContainerHealth` whenever it likes and receive their answers (`bins/executor/src/main.rs:342-397`). All three kinds of read share one single-flight gate, so they run one at a time (`bins/executor/src/main.rs:343-346`, `:364-367`, `:371-374`). At most one inventory read can be stranded at once (`bins/executor/src/main.rs:299`). The role accepts at most eight connections (`bins/executor/src/main.rs:271`). The role has no write request. Its unit records that UID 0 keeps owner write on root-owned files there, so only the code holds that back.

Target preparation (`limeos-storage-targets`) is dormant. It runs as root with only `CAP_CHOWN`, and only when the operator has created its ceiling (`packaging/systemd/limeos-storage-targets.service`). Core can create empty mount-target directories for a contract in which every device is a listed UUID and mountpoint pair (`crates/executor-protocol/src/lib.rs:419-437`, `bins/executor/src/storage_targets.rs:72-95`, ADR 0010). The role runs one operation at a time (`bins/executor/src/storage_targets.rs:41`, `:67-69`).

Mounts (`limeos-storage-mounts`) are dormant. The unit has no `[Install]` section, needs five protected files and sets `Restart=no` (`packaging/systemd/limeos-storage-mounts.service`). It runs as root, and every process in it holds `CAP_SYS_ADMIN`, `CAP_SYS_PTRACE` and `CAP_DAC_READ_SEARCH`. Core can mount a listed target's ext4 filesystem at its listed mountpoint without an fstab entry. Admission checks the filesystem type, and the mounted result must be `nosuid,nodev` (`crates/executor-storage/src/mount_admission.rs:538`, `:868-870`). There is no unmount request. This role rereads its ceiling on each connection and between the stages of an execute (`bins/executor/src/storage_runtime.rs:71`, `:202-233`, `:371-378`), so revoking a target takes effect at once.

What is explicitly not defended.

- An executor cannot tell an operator-approved plan from one that core made up.
- Nothing limits how often core performs an allowed action. Repeated restarts and stops of listed containers, or a mount of a listed target, are within the model.
- The `principal` in a plan and the `resolved_by` in a resolution are what core says they are.
- No record of effects exists that core cannot shape. Receipts are pruned. Closures and resolutions are written on core's request. The container executor writes no journal line per effect; it logs only refusals and failures (`bins/executor/src/main.rs:52`, `:671-711`).
- Read requests are bounded by the role's flags, not by the managed lists.
- The container, host and reader ceilings are read once at start, with an lstat of the final path only (`bins/executor/src/main.rs:186-197`). Revoking a container needs an executor restart. `Ceiling::configuration_valid` does not reject `core_uid == 0` (`crates/executor-protocol/src/lib.rs:440-461`). Only package configuration compares it with `limeos-core`'s UID (`packaging/debian/postinst:57`, `bins/ctl/src/main.rs:118-125`). The storage ceilings already reject UID 0 (`crates/executor-protocol/src/lib.rs:399`).
- A flaw in a root executor itself, in the kernel or in root's own accounts is out of scope.

Consequences. Listing a container ID in `container.json` grants the listed actions on it to core, and to anyone who controls core, without approval or limit. Operators should list only containers they would accept being restarted or stopped at will, and should treat each storage target ceiling the same way. Because container ceilings are keyed on IDs, recreating a container drops it out of the ceiling until the operator edits the file and restarts `limeos-containerd`. That fails closed. Enabling the dormant storage effect roles extends this model to root mounts and directory creation. This ADR is the documentation part of PR-30 only.

Follow-ups, none of them done:

- PR-30: a per-resource action rate limit enforced in the executor, and an append-only executor-side action log that core cannot rewrite.
- PR-31: load every ceiling through `read_protected_json` (no-follow walk, reread per request) and reject `core_uid == 0`, which the storage ceilings already do. Decide between names and IDs as ceiling keys.
- PR-32: run the storage reader as a dedicated user, and hold `CAP_SYS_ADMIN` only in the mounts helper (`docs/plans/2026-11-19-production-readiness-plan.md:90-93`).
