# ADR 0013: privileged executors trust core within their ceilings

Status: accepted by the owner, 2026-11-20, as the documented model for plan row PR-30 (`docs/plans/2026-11-19-production-readiness-plan.md`). This records the model and what the code enforces today. The executor-side effect budget and action log that PR-30 also asks for were added on branch `pr-executor-limits` (23 November); they are described under "Effect budget and action log" below. Plan row PR-31 (2026-11-23) changed how the host, container and reader roles read their ceiling and made every ceiling refuse `core_uid` 0; the paragraphs below describe the code after that change. Plan row PR-32 (2026-11-24, branch `pr-reader-user`) moved the storage reader from root to its own account; the reader's paragraph below describes that.

Context. Core (`limeos-core`) is unprivileged and network-facing. It authenticates administrators, checks grants and approval tokens, and dispatches work to separate executor processes over Unix sockets. Most executors hold a privilege that core lacks: the container executor has Docker group membership, the storage reader has Docker group membership and `CAP_DAC_READ_SEARCH`, and the storage effect roles run as root. The host executor (`limeos-storaged`) holds none: it runs as its own unprivileged user with no capability (`packaging/systemd/limeos-storaged.service:10-18`). The architecture already says core is a trusted component that, if compromised, "could misuse operations allowed by that ceiling and fabricate its own internal approvals" (`docs/plans/2026-10-04-rust-rewrite-architecture.md:146`). ADR 0003 says the executor "trusts core within the root-owned ceiling and does not verify approvals" (`docs/adr/0003-p03-durable-container-operations.md:21`). The production-readiness plan asked the owner to accept that model or to require an independent approval path before any storage effect ships (`docs/plans/2026-11-19-production-readiness-plan.md:137`). The owner accepted the model.

Decision. An executor performs any well-formed request from core's UID that its role's root-owned ceiling allows. It does not re-authorize the administrator. No approval token or session reaches an executor. The only user identities that reach one are those core asserts: a plan's `principal` (`crates/domain/src/operations.rs:164`) and a resolution's `resolved_by` (`crates/executor-protocol/src/lib.rs:196-197`), which the executor checks for format only and records. Core checks the approval when it queues a job (`crates/persistence/src/plans.rs:233`). It re-checks the grant and the plan's expiry right before dispatch (`bins/core/src/operations.rs:534-551`). It then sends only the action ID, the plan digest and the plan (`bins/core/src/operations.rs:565-576`). The executor accepts the plan if four checks pass. The plan hashes to the digest it carries (`crates/executor-container/src/lib.rs:456-460`). Its lifetime is at most 300 seconds and has not expired (`crates/domain/src/operations.rs:7`, `:174-191`). A fresh Engine inspection equals the plan's expected snapshot (`crates/executor-container/src/lib.rs:485-488`). The target is within the ceiling as the file says at that request (`crates/executor-protocol/src/lib.rs:808-834`, rechecked in `crates/executor-container/src/lib.rs:58-100`). The plan's `principal` and `grant_revision` are checked for format only (`crates/domain/src/operations.rs:176-179`). Core can read the same fresh inspection through the `Inspect` request (`crates/executor-protocol/src/lib.rs:658-666`). So a core that is compromised can mint a plan the executor accepts, whenever it wants.

What bounds a compromised core today.

- Socket access. Each socket is created mode 0660 (`bins/executor/src/main.rs:258`, `bins/executor/src/storage_targets.rs:38-39`, `bins/executor/src/storage_runtime.rs:55-56`). It lives in a runtime directory of mode 0750, group `limeos-container-access` or `limeos-host-access` (`packaging/systemd/limeos-containerd.service`, `packaging/systemd/limeos-storaged.service`). Core holds both groups (`packaging/systemd/limeos-core.service`).
- Peer credentials. Every role reads its ceiling when a connection is accepted and compares the SO_PEERCRED UID with that ceiling's `core_uid` before it reads a frame, then reads the ceiling again once the frame has arrived and authorizes the request against that second read only, peer included (`bins/executor/src/shared_role.rs:66-81` through `CeilingFile::for_peer`, `bins/executor/src/ceiling.rs:143-151`; `bins/executor/src/storage_targets.rs:67-77`; the mounts role reads it again in `dispatch` and between the stages of an execute, `bins/executor/src/storage_runtime.rs:74`, `:99-100`). So holding a connection open across a revocation gains a compromised core nothing. The comparison repeats in `Ceiling::validate` and in every authorize call (`crates/executor-protocol/src/lib.rs:610`, `:795`, `:816-817`). Frames are capped at 64 KiB (`crates/contracts/src/lib.rs:16`, `:302`).
- Role split. The role is fixed by argv at start (`bins/executor/src/main.rs:186-200`). The host and storage-reader roles refuse any ceiling that grants writes or logs, the shadow's read-only container role refuses writes, the reader refuses a ceiling without a storage read, and the other roles refuse the reader's flags. `Ceiling::admit` makes these checks with the `core_uid` and form checks on every read of the ceiling, not only at start (`crates/executor-protocol/src/lib.rs:578-608`), and `limeosctl check-ceiling FILE CORE_UID ROLE` runs the same walk and the same `admit` (`bins/ctl/src/ceiling_check.rs`). The storage effect roles insist on their fixed policy path, socket, binary and root (`bins/executor/src/storage_targets.rs:14-23`, `bins/executor/src/storage_runtime.rs:27-37`).
- Ceilings and what they are keyed on. Container ceilings list full 64-hex Engine container IDs, not names (`crates/domain/src/operations.rs:122-127`, `crates/executor-protocol/src/lib.rs:513-517`, `:829`); PR-31 kept that keying, since names or IDs is still the operator's decision. Stack ceilings list Compose project names, and every member the action targets must also be a listed container ID (`crates/executor-protocol/src/lib.rs:789-807`). Only targets are checked: running members for restart and stop, stopped members for start (`crates/domain/src/stack_operations.rs:97-103`). So an accepted stack may contain unlisted members that the action skips; the executor acts only on targets, and those members stay untouched. Storage ceilings list exact filesystem UUID and mountpoint pairs under `/mnt/`, and mounts also name a target ID (`crates/executor-protocol/src/lib.rs:296-437`). Every ceiling is read through the same descriptor walk: each component from `/` is opened without following symlinks and must be root-owned and not group- or world-writable, and the file must be a regular file with one link and at most 64 KiB (`crates/executor-storage/src/path.rs:90-144`, `crates/executor-storage/src/targets.rs:44-145`). A symlink or a component of the wrong type (ELOOP, ENOTDIR), the wrong owner or a writable mode is an unsafe path; a missing file, a permission refusal (EACCES, EPERM), a malformed file and a transient failure (EMFILE, ENFILE, ENOMEM, EINTR, I/O) are each reported as such (`crates/executor-storage/src/path.rs:60-70`). The unprivileged host and container roles and the reader use `read_root_owned_json`, the walk without `read_protected_json`'s root check; the target role uses the same walk after refusing to start as anything but root, and the mounts role checks root on each read (`bins/executor/src/ceiling.rs:153-158`, `bins/executor/src/storage_targets.rs:155-202`, `bins/executor/src/storage_runtime.rs:377-418`). Every ceiling refuses `core_uid` 0 (`crates/executor-protocol/src/lib.rs:401`, `:512`, `:583`), and the startup error says so. The package installs read-only defaults: the container ceiling grants no effect and lists no container (`packaging/debian/postinst:55-73`).
- One effect at a time. Container effects share one receipt-store lock taken with `try_lock` (`bins/executor/src/container_requests.rs:60-64`). A unique index refuses a second action on a resource while one is prepared, accepted or unknown (`crates/executor-container/src/lib.rs:243`).
- An effect budget per container, enforced by the container executor alone: at most 10 effects in any ten minutes and 60 in any day, counted from its own action log (`crates/executor-container/src/limit.rs`; see below).
- systemd sandboxing, per unit (see the role list below).
- Receipts in executor-owned stores. Core cannot open them. The container store directory is 0700 and owned by `limeos-containerd` (`packaging/debian/postinst:51`). The store refuses any other owner or mode (`crates/executor-container/src/lib.rs:173-200`). A replayed action ID returns its stored receipt instead of running again (ADR 0003).
- Log redaction in the executor. Container logs are redacted before they leave the container executor, so core receives redacted text (`crates/executor-container/src/logs.rs:1-2`).

What a compromised core can and cannot do, per role.

The container executor (`limeos-containerd`) is enabled by default (`packaging/debian/postinst:82`). It runs as `limeos-containerd` with the `docker` group, no capabilities, `AF_UNIX` only and `ProtectSystem=strict` (`packaging/systemd/limeos-containerd.service`).

- With the default ceiling, core can read only. It can observe every container (`Observe`), inspect any container by ID (`Inspect`), list the members of any Compose project (`InspectStack`) and read the Engine storage inventory (`ContainerStorageInventory`). The single `allow_container_read` flag gates all four, and they are not limited to the managed list (`crates/executor-protocol/src/lib.rs:622-666`, `:701-707`). Logs require `allow_container_logs` and a listed container (`crates/executor-protocol/src/lib.rs:678-692`).
- Once the operator grants `allow_restart`, `allow_start`, `allow_stop` or `allow_stack`, core can perform the granted action on any listed container or stack, within the effect budget: each listed container takes at most 10 effects in any ten minutes and 60 in any day, whatever mix of restart, start, stop and stack actions spends them. It can verify each action itself with a fresh inspection (`crates/executor-container/src/lib.rs:538-583`) and send the next one. Keeping every listed container stopped is within the ceiling and costs one effect each; a restart loop is bounded to 60 restarts of a container a day (at most 64 listed containers, so at most 640 effects in ten minutes and 3,840 a day in all). Every effect, and every refusal by the budget, is recorded where core cannot change it.
- It can also write receipt rows through requests. A lookup with `close_if_absent` writes a closure for any action ID (`crates/executor-container/src/closure.rs:229`). `ResolveAction` marks a stuck action resolved and frees its lock (`crates/executor-container/src/resolution.rs:123-151`). It records whatever `resolved_by` ID core supplies, behind evidence core can compute. Retention prunes toward 1024 container and 256 stack receipts (`crates/executor-container/src/retention.rs:81-83`), but these are pruning budgets, not hard limits. Pruning removes only settled receipts, which hold no lock, and only once their plan has been expired for at least an hour (`RETAIN_AFTER_EXPIRY`, 3600 s), oldest expiry first and at most 64 rows per new receipt (`crates/executor-container/src/retention.rs:19-23`, `:251-266`). Unsettled receipts are never pruned, and the store refuses new actions at 8192 rows (`crates/executor-container/src/lib.rs:388-393`). Churning rows can therefore prune only settled receipts whose plans expired more than an hour earlier.
- It cannot act on an unlisted container or project. It cannot create, remove, exec, pull or change images or networks: the protocol has no such request (`crates/executor-protocol/src/lib.rs:43-211`), and the Engine trait reaches only fixed endpoints (`crates/executor-container/src/lib.rs:110-127`, `crates/executor-container/src/docker.rs`). It cannot reach the Docker socket itself: the package refuses Docker membership in `/etc/group` for every other service account (`packaging/debian/postinst:13-15`); the storage reader's Docker access comes from its own unit's `SupplementaryGroups=`, which core's unit does not have. It cannot change a ceiling, which is root-owned.

The host executor (`limeos-storaged`) is enabled by default. It runs as `limeos-storaged` with no capabilities, `PrivateNetwork`, `ProtectSystem=strict` and `~@privileged` (`packaging/systemd/limeos-storaged.service`). Its ceiling grants health and host reads (`packaging/debian/postinst:62`). Core can read host metrics, ask for a more active collection cadence (`bins/executor/src/shared_role.rs:141-160`) and ask for health. Every other request is refused (`crates/executor-protocol/src/lib.rs:609-620`, `bins/executor/src/container_requests.rs:218`).

The storage reader (`limeos-storage-reader`) runs as its own account, `limeos-storage-reader` (primary group `limeos-host-access`), without a mount namespace. It holds `CAP_DAC_READ_SEARCH`, ambient, for read-only opens of block devices and `blkid`'s reopen of them, and the `docker` group from its unit for the GET-only stack and container-health reads; the fixed readers refuse to run without root or that capability (`full_read_access` in `limeos_executor_storage`, with an identical copy in `limeos_executor_container`). Its unit has no `[Install]` section, and the package does not enable it; the basic cutover starts it (`packaging/systemd/limeos-storage-reader.service`, `scripts/cutover/activate.sh`). Core trusts its socket by the container executor's rule, one implementation for both (`limeos_contracts::ExecutorOwner`): the socket is owned by an account that is neither root nor core, and the kernel names that account as the peer; a root-owned reader socket is refused. Before PR-32 the reader ran as root and core required a UID 0 peer. Its ceiling must be read-only (`crates/executor-protocol/src/lib.rs:578-608`). Core can trigger the reads behind `StorageInventory` and the nonce-bound `ContainerHealth` whenever it likes and receive their answers (`bins/executor/src/shared_role.rs:84-98`, `:113-140`). `StackInventory` answers from a cache (`bins/executor/src/shared_role.rs:99-104`); the reader refreshes it itself every 30 seconds, when the ceiling read before that pass grants stack reads (`bins/executor/src/main.rs:263-289`), so a request never triggers a read. The two request-driven reads and the periodic stack scan share one single-flight gate, so they run one at a time (`bins/executor/src/main.rs:282`, `bins/executor/src/shared_role.rs:85-89`, `:114-118`). At most one inventory read can be stranded at once (`bins/executor/src/main.rs:295`). The role accepts at most eight connections (`bins/executor/src/main.rs:259`). The role has no write request. As its own account it no longer has root's owner write on root-owned files or on the disks; it owns only its runtime directory and socket. What it still has: `CAP_DAC_READ_SEARCH` lets it read every file (root's owner read of the raw disks already did), and Docker access is root-equivalent, so code execution in the reader still reaches root through dockerd (the same holds for the container executor). Without a mount namespace it cannot have `ProtectHome`, `PrivateTmp` or `ProtectSystem`. If a compromised core could make the reader run code of its choosing, it would gain that; core can only send the reader's read requests.

Target preparation (`limeos-storage-targets`) is dormant. It runs as root with only `CAP_CHOWN`, and only when the operator has created its ceiling (`packaging/systemd/limeos-storage-targets.service`). Core can create empty mount-target directories for a contract in which every device is a listed UUID and mountpoint pair (`crates/executor-protocol/src/lib.rs:419-437`, `bins/executor/src/storage_targets.rs:72-95`, ADR 0010). The role runs one operation at a time (`bins/executor/src/storage_targets.rs:41`, `:67-69`).

Mounts (`limeos-storage-mounts`) are dormant. The unit has no `[Install]` section, needs five protected files and sets `Restart=no` (`packaging/systemd/limeos-storage-mounts.service`). It runs as root, and every process in it holds `CAP_SYS_ADMIN`, `CAP_SYS_PTRACE` and `CAP_DAC_READ_SEARCH`. Core can mount a listed target's ext4 filesystem at its listed mountpoint without an fstab entry. Admission checks the filesystem type, and the mounted result must be `nosuid,nodev` (`crates/executor-storage/src/mount_admission.rs:538`, `:868-870`). There is no unmount request. This role rereads its ceiling on each connection and between the stages of an execute (`bins/executor/src/storage_runtime.rs:71`, `:202-233`, `:371-378`), so revoking a target stops every execute that has not yet released its helper. The final policy check runs just before the helper is sent GO (`bins/executor/src/storage_mount_supervision.rs:366-376`). A revocation after that cannot cancel a helper already released, and its mount goes ahead.

What is explicitly not defended.

- An executor cannot tell an operator-approved plan from one that core made up.
- An allowed action can be repeated up to the effect budget: 10 effects per listed container in ten minutes, 60 in a day. Stopping a container needs one effect, so the budget bounds churn, not downtime. A mount of a listed target, and target preparation, have no budget (see below).
- The `principal` in a plan and the `resolved_by` in a resolution are what core says they are.
- The action log shows what the container executor did, not who approved it: the principal it records is the one core named. Core cannot rewrite it, but it can push its oldest rows out by spending budget (below), and anyone with root can edit it. Receipts are pruned, and closures and resolutions are written on core's request, as before. The storage effect roles keep no action log.
- Read requests are bounded by the role's flags, not by the managed lists.
- Ceilings are reread for each request, not watched. Each connection reads its ceiling twice, at accept and after the frame, and only the second read authorizes the request. What remains: a request already authorized runs to its end (an execute, a log read, a target preparation), so a revocation stops the next request, not one in flight; the mounts role narrows that window with its rereads between stages, as above. A reread costs one walk and one parse: 23 µs on a development laptop for the largest ceiling the format allows (release build, `ceiling_read_cost`; not measured on the Pi), so about 45 µs per request. Core asks each executor about once every 10 s when active and 60 s when idle, so the rereads cost well under 0.01% of one core.
- What a role set up at start from its first read stays until a restart: whether the container executor opened its receipt store, whether an observation collector runs, and whether the reader's stack scan exists (the scan rereads the ceiling before every pass and skips the pass when stack reads are no longer granted). Narrowing takes effect on the next request. A request that a later ceiling grants but that needs one of those is answered `Unavailable`, never with an empty result core could take for a real one: receipt-store requests and `ReceiptEpoch` (`bins/executor/src/container_requests.rs:46-49`, `:216-219`), `Observe` without a collector and `StackInventory` without a scan (`bins/executor/src/shared_role.rs:100-102`, `:149-151`).
- A ceiling that cannot be read or admitted refuses every request; no earlier copy is kept. Such a refusal is `Unavailable` in every role, never `Forbidden`: core withdraws an operator's resolve request on `Forbidden` (`bins/core/src/job_resolution.rs:431-440`) but keeps it pending on `Unavailable`, so a half-written file during an in-place edit, or a missing or unsafe one, cannot withdraw it. `Forbidden` is kept for a ceiling that was read and says no, and for a peer that is not core. That includes a well-formed request of a kind the ceiling's flags do not grant, which used to fall through to `InvalidInput`: with every effect flag off, a resolve request now gets `Forbidden` and core withdraws it with a final answer instead of retrying it every pass (`Ceiling::grants`, `crates/executor-protocol/src/lib.rs:536-577`, `:613-620`). `InvalidInput` is left for another protocol version or malformed fields. The refusal is logged on each change of refusal kind and on recovery, in all four roles (`bins/executor/src/ceiling.rs:62-90`). A bad edit leaves a running executor answering `Unavailable`, with nothing failing visibly. Its next restart fails, since startup still reads the ceiling and refuses a bad one (`bins/executor/src/main.rs:210-212`, `bins/executor/src/storage_targets.rs:31-34`, `bins/executor/src/storage_runtime.rs:41`). A package configure runs the same check on each existing shared ceiling. One it refuses gets a one-line warning, and that executor is left unstarted while everything else starts; configure does not fail, because that would leave every unit prerm stopped down and apt blocked for a file the executor refuses anyway (`packaging/debian/postinst`, `docs/p01-operations.md`). So operators check edits with `limeosctl check-ceiling` first (`docs/p03-operations.md`).
- Revoking a container strands its open actions. Receipt lookup, verification and resolution of an existing receipt re-check the container against the current ceiling (`crates/executor-container/src/closure.rs:157`, `:193`, `crates/executor-container/src/lib.rs:559`, `crates/executor-container/src/resolution.rs:164`, `:176`). A container removed between its execute and core's verification leaves the job `needs_intervention` with its locks held, and resolution is refused, and core withdraws the resolve request, until the container is listed again. `docs/p03-operations.md` gives the operator procedure. Whether these re-checks should be relaxed is open.
- A flaw in a root executor itself, in the kernel or in root's own accounts is out of scope.

Consequences. Listing a container ID in `container.json` grants the listed actions on it to core, and to anyone who controls core, without approval, up to the effect budget. Operators should list only containers they would accept being restarted or stopped at will, and should treat each storage target ceiling the same way. Because container ceilings are keyed on IDs, recreating a container drops it out of the ceiling until the operator edits the file; the edit takes effect on the next request, without a restart. That fails closed. Removing an ID or a flag likewise takes effect on the next request, and strands any open action on it until it is listed again. Enabling the dormant storage effect roles extends this model to root mounts and directory creation. The container executor bounds and records those actions itself ("Effect budget and action log", below).

Effect budget and action log (PR-30). The container executor is the only trusted party that sees every effect, so it bounds and records them itself (`crates/executor-container/src/limit.rs`).

- What is limited. Every new effect on a container: restart, start and stop share one budget per container, and a stack action charges each target it acts on one effect. A stack is admitted whole or refused whole (`execute_stack` checks every target before it prepares anything). Only new effects are charged: a replayed action is answered from its receipt before the budget is read, and receipt lookups, closures, verification and resolution never reach it (`limit/tests.rs`, `resolution/tests.rs`). The key is the container ID the ceiling matched exactly, which the fresh inspection must equal (`check_current`), so another spelling is refused by the ceiling before the budget is read, a new action ID, plan ID or digest is just another effect, and a stack member and the same container alone spend one budget.
- The numbers. 10 effects in any 600 s and 60 in any 86,400 s, per container, constants in the code. A person debugging a container restarts it a few times in ten minutes; a stack restart is one effect per member; future automation may only propose, and a person approves every plan (ADR 0003, ADR 0005), so plans arrive at human pace. Ten in ten minutes is one a minute; 60 a day is six such sessions on one container. Without a budget a compromised core could restart a container every few seconds, all day; with it a restart loop costs a container about ten minutes of downtime a day at ten seconds a restart. There is no budget shared between containers: effects on one container never refuse an effect on another. That is the trade-off core's login limiter made, which refuses a shared budget that one name's failures could spend for every other (`docs/p01-operations.md`, commit `89ccfbf9`); here a shared budget would also add nothing against a compromised core, which needs one stop per container to deny service. The numbers are constants rather than ceiling fields: core cannot raise them either way, a household has no reason to tune them, and a constant cannot be misconfigured or fail to parse; a field can be added if a real need shows.
- Source of truth. The action log is a table of the receipt store, `effect_log`: one `effect` row per container charged, written in the transaction that prepares the action, so an effect is never uncharged and a charge never lacks its receipt. The budget is a count of a container's effect rows inside each window, whatever their outcome, so it survives a restart of the executor without a counter of its own; a crash-looping or restarted executor gives nothing back. A charge is never refunded. A member never sent (its stack stopped at an earlier member, or the plan expired between prepare and the Engine call) is recorded `not_sent` and still counts: core writes the plan's expiry, so it can aim it at that moment and leave charged-but-unsent rows at will, and if those rows cost no budget they could fill the log, evict the rows that still count for other containers and admit more effects inside the same day (two reviews found this in the first version, which refunded them). The check and the charge are not one SQL transaction; they are atomic because every execute holds the receipt store's mutex for its whole call and nothing awaits between them (`limit.rs`, "Atomicity"). Receipt schema 9 adds the tables; a store upgraded then starts with an empty budget.
- Clock. Rows carry the wall clock, the clock that validates plans and the only one that means the same after a reboot. A row counts while it lies within one window of now in either direction. A row dated a little after now (the clock stepped back by less than the window) still counts, so the step holds a charge longer, the strict direction. A row further in the future (a clock without a battery that ran ahead and was corrected) no longer counts, so a large backward step gives a container its budget back at most once, as a forward step of more than the window does by ageing every row; without that bound, ten charges taken while the clock ran three years ahead would refuse the container for three years after the correction. The receipt barrier does not cover this: its watermark moves only when receipts are pruned, so a store that has pruned nothing refuses no plan after any step. What a backward step of more than a day can do: every container takes one more day's budget while its earlier charges sit in the future, held but not counted (at most 60 more effects per container per such step), and those earlier charges count again once the clock is corrected, so the container may then be refused for up to a day longer than its corrected history alone says. Repeated large steps within a day can fill the log with held charges; it then refuses every effect until the oldest is a day old by the corrected clock (`charges_that_can_still_count_survive_a_clock_stepped_back_and_corrected`, `a_log_full_of_charges_that_can_count_refuses_instead_of_evicting`). Core cannot set the clock; an attacker on the LAN who can step it through unauthenticated NTP is out of scope.
- Failure. A budget that cannot be read refuses the effect with `StateNotDurable`, before prepare, like any store failure there (core holds such a job for an operator, as before). A refusal by the budget answers `RateLimited`, a code added for it, with `budget_frees_at`: the earliest time, by the executor's clock, when every container the action would charge has room in every window, counting every charge the log holds that will count then, those dated in the future included (`the_free_time_counts_future_charges_that_will_enter_the_window`). A further backward clock step can move it later. Core settles a job refused with it directly as `precondition_changed`, releasing its locks, with no lookup and no operator, as it does for `BeyondReceiptHistory`: the refusal comes after the replay check and before prepare writes a receipt or the Engine is asked to act, and core sends one execute per job (`refused_before_any_row`, `bins/core/src/operations.rs`). The job's history records an `executor_budget_spent` event with that time, which the web interface shows as "refused: the effect budget of a container it acts on is spent until …". Leaving the job queued would not help: its plan expires within five minutes.
- Refusals. A refusal row is written for a container only when none of its refusal rows lies within an hour of now in either direction, carrying the number of refusals counted since the last one in this process (in memory, lost on a restart). So a flood of refused requests costs at most one write per listed container an hour, a clock stepped back a little delays rows rather than multiplying them, and one stepped back a long way does not silence them. Refusals for other reasons (an unlisted container, a stale plan) write nothing, as before.
- Bounds. The log holds at most 8,192 rows, removed oldest first in the inserting transaction, but never a charge that can still count: one dated less than a day before now, or in the future, where a clock stepped back can bring it into a window later. So budget state is never evicted, whatever the clock does. When the log is full of such charges, every new effect is refused (`RateLimited`, with the time the oldest of them stops being able to count) and no refusal row is written, rather than evicting one. Every row the log can hold is bounded by the budget or the refusal rule: with the clock steady, a container has at most 60 effect rows of any outcome (each admitted by the budget) and 25 refusal rows in any day, and 64 listed containers at most 5,440 rows a day, so the log never fills with charges that can count and never refuses for room (a compile-time assertion over both classes; `limit/tests.rs` runs a day of plans aimed at the expiry, single and as stacks, and checks another container's charges survive). `effect_days` keeps, per day, the containers charged (sent or not) and the refusals the day's refusal rows stand for (a coalesced row books refusals from up to an hour earlier to the day it is written), for 400 days. A row of the longest values the protocol admits (a 128-byte principal, a 64-character project) costs 521 bytes with its index, so a full log is 4.3 MB (1,040 pages) inside the receipt store. Beside saturated receipt retention (1,024 receipts and 256 stacks) the store is 10.8 MB (2,636 of its 4,096-page cap) with every stack at the protocol's 16 members, and 7.6 MB, inside the soak's 8 MiB bound, with stacks the size of the soak's largest (6) (`a_full_log_beside_saturated_receipts_stays_within_the_store_cap`); an earlier estimate of 300 bytes a row and 3 MiB was low. The executor's open runs `quick_check`, which reads every page, so a full log adds about 1,040 page reads (4.3 MB) to an open: a fraction of a second on an SD card, once per executor start (not measured on the Pi). The soak's receipt store, whose log is far from full, went from about 700 to about 1,600 page reads at open with the storm's rows. At household rates (a few charges a day) 8,192 rows are more than a year.
- Where it lives, and who can change it. `/var/lib/limeos/executors/container/receipts.sqlite`, a 0600 file in a 0700 directory owned by `limeos-containerd`, under `/var/lib/limeos/executors` owned by root with mode 0755 (`packaging/debian/postinst`), with `UMask=0077` in the unit; the store refuses another owner or a group- or world-accessible mode. Core's account cannot read, write, truncate, rename or delete it, and core's unit can write only `/var/lib/limeos/core` (`ProtectSystem=strict`). The executor's own account and root can change it.
- What a compromised core can do to the evidence. It cannot alter a row. It can push rows out of the log only with rows the budget or the refusal rule admits, charged-but-unsent ones included: 8,192 newer rows take at least a day and a half at the most every listed container can be charged and refused (5,440 a day), and those rows are themselves the record of the flood; the daily totals keep the volume of the days whose rows went. It can write journal lines of its own, but each carries its unit, and it can rotate the system journal by writing heavily, which is why the table, not the journal, is the record.
- Reading it. `sudo -u limeos-containerd /usr/lib/limeos/limeosctl action-log [--limit N]` prints the newest rows as JSON lines, then the daily totals (`bins/ctl/src/action_log.rs`); it opens the store read-only and refuses to run as any account but the store's owner, since files root created beside the store could stop the executor opening it. The executor also writes one journal line per row (`action log: effect` at info, `action log: effect refused` at warning, `bins/executor/src/container_requests.rs`), for `journalctl -u limeos-containerd --grep 'action log'`; journald's retention and size are the host's, and those lines are a convenience, not the record. `docs/p03-operations.md` has the procedure.
- What it proves. That the container executor performed, or refused, an effect on that container at that time (by the clock then) at the request of that peer UID (always core's), naming that principal, and with what outcome. Not that a person approved it: the principal is core's word. Not that nothing else touched the container: Docker itself, or anyone in the `docker` group, acts outside it. And nothing about a store that was deleted, replaced or restored, which loses or rewinds it, as it does receipts.
- Not covered. The storage roles: target preparation and mounts are live code in the default build (the `deferred` feature gates no effect path; its executor part, `updates`, is planning only) but dormant, installed without being enabled. They have no budget and no action log. Their effects are monotone: preparation creates empty directories that then exist, and a mount of a listed target cannot be undone by any request, since there is no unmount, so repeating either gives a compromised core nothing one request does not; each role already runs one operation at a time and keeps its own receipt journal. Before either is enabled, its effects should join an action log (plan row PR-43's shared receipt journal is the natural place). The shadow container executor is read-only and has neither. The host executor and the storage reader perform no effect.
