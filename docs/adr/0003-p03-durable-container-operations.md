# ADR 0003: durable container operation authority

Status: accepted and implemented for the restart path, 2026-10-05. Implements architecture A04 and roadmap RW-030.

Core creates a typed `container.restart@1` plan from a selected, fresh Docker inspection. The plan binds the complete container ID, image ID, running state and last start timestamp, its owner and grant revision, a normalized digest and a five-minute expiry. The registry owns the operation's risk, scope, timeout and recovery classification. Caller text never sets them.

A separate human-session approval binds that digest. Core stores only the digest of a random approval token; the token is single-use, expires with the plan, and cannot approve a modified or newly resolved resource. Queuing consumes approval and records intent plus audit events in one FULL-synchronous SQLite transaction. Browser and future assistant proposals use the same plan and policy definitions; possession of an assistant task token will not constitute human approval.

Idempotency keys belong to the principal. Repeating a queued request with the same plan returns the original job; changing the plan conflicts. A revoked grant invalidates pending approval and dispatch. The executor must independently inspect the resource again immediately before an effect and enforce its root-owned allowlist.

Cancellation of waiting or queued work records a terminal state without a host effect. Once dispatch is uncertain, core retains the per-resource lock and requires reconciliation. Cancellation must never label an in-flight restart as if it had been prevented.

Authority schema v2 adds plans without rewriting the v1 tables. A transactional migration preserves existing identity, jobs and audit state. The v1 binary refuses the newer schema; automatic downgrade across this migration requires recovery rather than being advertised as compatible.

A protected executor receipt is committed before dispatch and deduplicates action IDs across interruption. Core records the authenticated receipt with independent selected inspection evidence in schema v3. Both resource locks remain held until a fresh new running incarnation is verified; executor verification performs another inspection before releasing its lock. Recovery reads receipts and never sends an effect request for an interrupted job. Missing or prepared receipts retain `needs_intervention`.

Session mutations recheck authentication inside the final authority transaction after inspection. Scoped task callers resolve their principal from a token bound to their kernel UID, task, scope, grant revision and core generation. Their protocol offers proposal and approved queueing, with no approval command. Duplicate queue requests recover the original job from durable state without contacting Engine. Schema v3 migrates v1/v2 transactionally and records receipt plus verification with the terminal job event.

Retention (PR-11, receipt schema v6): each receipt records its plan's expiry. Settled receipts (`verified`, `precondition_changed`, operator-`resolved`, and a stack's `partly_done`) beyond 1024 container and 256 stack receipts are pruned, oldest expiry first and at most 64 rows per insert, once their plan has been expired for an hour. A stack goes with all its member rows or not at all, so a batch stops before a stack that would take it past 64 rows; one whole stack (at most 17 rows) always fits, so a batch over budget always makes progress. Receipts that hold a lock (`prepared`, `effect_accepted`, `outcome_unknown`) are never pruned. A `resolved` row is pruned like other settled history (a resolved stack with its members): kept forever, every resolution would turn prunable history into a permanent row until the last-resort caps stop all execution. A core that crashed after the executor recorded `resolved` but before completing its own side retries `ResolveAction`, and gets the stored confirmation while the row is kept, or, once it is pruned, a closure answered `no_longer_held` (see below), after which it completes on a fresh measurement matching the approved evidence. A repeated action whose receipt was pruned is refused by the execute barrier below (`beyond_receipt_history`, its plan expires at or below the watermark) before any clock is read. The 8192-row and 16 MiB caps remain only as last-resort stops.

Replay protection and its horizon: while a receipt is retained, closures included, its action id is bound to one plan digest. The same request returns the stored receipt without a second effect, and the same id with any other plan is `Conflict`. That binding lasts at least until the plan has been expired for `RECEIPT_RETAIN_AFTER_EXPIRY`, and for settled receipts only until retention needs the room; lock holders keep it indefinitely. The original plan itself cannot run again after pruning: its expiry is at or below the watermark, so the execute barrier refuses it whatever the clock says. A new valid plan (fresh timestamps, its own digest) presented under a pruned id is unknown to the executor and executes as a fresh id would. That is not an escalation: the executor trusts core within the root-owned ceiling and does not verify approvals, so a caller able to send that request could equally mint a fresh id. Approval, single use and idempotency of a human request are core's, bound to the job id core generates. `a_pruned_action_id_with_a_new_valid_plan_executes_like_a_fresh_id` pins this behaviour.

A missing receipt after pruning (receipt schema v7): the receipt store keeps a prune watermark, the greatest plan `expires_at` among every receipt it ever pruned, raised in the same transaction as each prune and never lowered. Receipt lookups and `ResolveAction` carry the plan itself, exactly as core stored it; the executor recomputes its digest, refuses the request as invalid unless it equals the plan digest the request names (and, for `ResolveAction`, unless the plan is of the named kind and well formed), and judges by that plan's own `expires_at`, never a bare number. With no row the executor answers `never_recorded` when that expiry is strictly above the watermark (no receipt for the plan can have been pruned, so none was written and nothing was sent) and `no_longer_held` otherwise. Equality is `no_longer_held`. The answer reads no clock, so a clock step after a prune cannot turn an executed action into an unsent one. Rows that existed at the upgrade to schema 7 are `legacy` (schema 6 back-filled their expiry from the upgrade clock); a pruned legacy row leaves its action ID in `pruned_legacy`, which always answers `no_longer_held`. A store opened at schema 6 may have pruned without a watermark and starts at the maximum.

Closing an action (receipt schema v8): an absence alone proves nothing about an execute request still on its way, which could reach the store later and prepare and run after core released the job, and waiting for the plan to expire is no barrier because the clock that judges expiry can step back (a Pi without a real-time clock). So a receipt lookup that carries `close_if_absent`, and every `ResolveAction`, records a closure when it finds no row: a terminal `precondition_changed` receipt for that action id and plan digest (the refusal row shape; a stack closes its stack row and one member row per target), written in one transaction under the store lock every execute takes. The absence is judged in that transaction before retention runs, and kept in the row's `closed` column. An execute and a closing lookup cannot interleave: the executor's handlers take one store mutex with `try_lock`, and contention is `Overloaded`, which core retries. If the execute prepared first, the lookup reports its row and closes nothing; if the closure was recorded first, the execute finds it in its replay check, before it reads a clock or contacts the Engine. A `never_recorded` closure is answered with its receipt and `closed`, and a late execute gets the same receipt back; a `no_longer_held` closure is answered with that absence and `closed`, and a late execute is refused with `Expired`, never told that nothing was sent, because the pruned receipt may record an effect. A lookup without `close_if_absent` is a status read and writes nothing; core sends none today, since every lookup it makes follows a lost execute answer (core runs one dispatcher, which awaits its execute call, so no lookup of its own overlaps an execute it is still waiting for). Writing a closure needs only the write authority the protocol ceiling already demands: it grants nothing and only takes an id out of use. Core records a closure receipt like any refusal: the stack or container job becomes `precondition_changed` and releases its locks at once, with no expiry wait (`execution_closed` and its margin are gone). On `no_longer_held` (or no answer) a stack or container job stays in (or moves to) `needs_intervention` with every lock and one `executor_receipt_missing` event; an absence the executor did not close keeps the job held and asked again. An operator resolution the executor answers with a closed absence completes as soon as core's fresh measurement matches the approved evidence, and is withdrawn when it does not. A `never_recorded` closure proves nothing was sent, so it allows only what a `precondition_changed` receipt allows (`not_done` or `accepted_divergence`): the executor refuses `verified_done` against it, found or just written, with a `ResolveRefusal`, and core withdraws such a request whatever the executor answered; a `no_longer_held` closure leaves every declaration to the operator; an absence without `closed` leaves the request pending for the retry loop. Closure rows are settled history: pruned under the rules above, never while their plan has been expired for less than `RECEIPT_RETAIN_AFTER_EXPIRY` by the pruning clock, and retired into the watermark, so a lookup after pruning closes the action again as `no_longer_held`. Only pruning eligibility reads a clock: a backward step delays it, and a forward step prunes early only a plan that clock holds expired by the full margin.

The execute barrier: once a closure is pruned, an execute request for its action finds no row, and after a backward clock step to before the plan's expiry both expiry checks would pass. So an execute for an action the store holds no row for is refused before prepare, with no Engine call, whenever its absence would be answered `no_longer_held`: its plan's `expires_at` is at or below the prune watermark (or its id is a legacy tombstone). Every receipt at or below the watermark may have been pruned, so the store can no longer tell whether that action was closed or already ran. The comparison is the absence rule's, non-strict: equality is refused, as equality is `no_longer_held`. It reads no clock, so a pruned closure followed by any clock step can no longer let a delayed execute run. The refusal is its own error code, `beyond_receipt_history`, which the executor and core both log with the probable cause. Its availability cost is deliberate: the watermark trails the pruning clock by at least `RECEIPT_RETAIN_AFTER_EXPIRY`, so only after a backward clock step of more than that margin plus the plan TTL do freshly approved plans also expire at or below it; they are refused (the job is held for an operator) until the clock passes the watermark again. That is the safe direction. No clock now decides whether an effect may run for an action the store has closed or pruned.

A new or changed receipt store (core authority schema v18; no receipt schema change): the watermark proves `never_recorded` only for the store that recorded everything since it was created, so a store that was lost and recreated, or restored from an older copy, must not certify an action it never saw. The executor answers this on both sides of the socket. A store created now cannot know what ran before it: its watermark starts at a creation floor, the executor's clock at creation plus the plan TTL. Plans carry absolute expiries from core's clock on the same host and are valid only while `expires_at <= created_at + PLAN_TTL_SECONDS`, so any plan approved no later than the store's creation expires at or below the floor and is answered `no_longer_held` (and refused at execute, by the barrier above); that is the tight bound, since any margin above it would refuse plans approved after the store existed. A clock that stepped back before the creation, or a store restored from an older copy, defeats a floor, so every open of the store also draws a random epoch, returned with every answer that read or wrote the store (execute, lookup, verify, resolve). The epoch changes on every open, not only at creation: a restored copy of the same store would carry an epoch fixed at creation, and any file swapped in is seen only after a reopen. Core keeps the epoch it last saw (`meta.executor_epoch`) and observes the epoch of every answer before acting on it; when it differs, every held container and stack job gets one `executor_store_changed` event in the same transaction. Separately, core never lets a closure overwrite a result it holds: a `never_recorded` closure for a job that already has a recorded result (other than that same closure), or that carries `executor_store_changed`, contradicts core's record, so nothing is released, the job moves to or stays in `needs_intervention` with every lock, and one `executor_record_disagrees` event records why; an operator then resolves it (a never-recorded closure accepts `not_done` or `accepted_divergence`). The first epoch core ever records is treated as a change like any other: on a fresh install nothing is held, and after the upgrade that added the epoch every held job was dispatched under none, so nothing ties it to the store now answering (a first execute whose answer was lost, followed by a store replaced by a pre-execution copy, would otherwise be released on a `never_recorded` closure); each such job is marked once. The cost of an epoch per open: after any executor restart, a job held across it whose execute never reached the store waits for an operator instead of being released by its closure.

Recovery polling is fair: each pass lists every queued job (oldest first, at most 64) and the next 64 held jobs by id after a cursor core keeps in memory, starting over after a short page, with each held job looked up at most once per 30 seconds. However many older jobs are held, every held job is reached within a bounded number of passes.

Recovery and an operator's resolution race by design, and whichever settles the job first wins: recovery keeps polling a job with an open resolution request, since it records only what the executor's receipt or closure proves, and holding it back would not exclude the race (a lookup already on its way when the request is recorded lands after it). A request whose job has left the held states can never complete, so it is closed as superseded: its row is deleted, as a withdrawn one is, and a `job_resolution_superseded` event (an authority event) records the state the job settled as, so the request no longer pins the job's history and the operator sees the job settled instead of a pending request. The retry loop supersedes such requests first, in bounded batches, and lists only requests whose job is still held, by job id after a cursor in rotation like held jobs, so no number of older requests can starve a newer one; a completion that loses the race supersedes its request itself.
