# ADR 0003: durable container operation authority

Status: accepted and implemented for the restart path, 2026-10-05. Implements architecture A04 and roadmap RW-030.

Core creates a typed `container.restart@1` plan from a selected, fresh Docker inspection. The plan binds the complete container ID, image ID, running state and last start timestamp, its owner and grant revision, a normalized digest and a five-minute expiry. The registry owns the operation's risk, scope, timeout and recovery classification. Caller text never sets them.

A separate human-session approval binds that digest. Core stores only the digest of a random approval token; the token is single-use, expires with the plan, and cannot approve a modified or newly resolved resource. Queuing consumes approval and records intent plus audit events in one FULL-synchronous SQLite transaction. Browser and future assistant proposals use the same plan and policy definitions; possession of an assistant task token will not constitute human approval.

Idempotency keys belong to the principal. Repeating a queued request with the same plan returns the original job; changing the plan conflicts. A revoked grant invalidates pending approval and dispatch. The executor must independently inspect the resource again immediately before an effect and enforce its root-owned allowlist.

Cancellation of waiting or queued work records a terminal state without a host effect. Once dispatch is uncertain, core retains the per-resource lock and requires reconciliation. Cancellation must never label an in-flight restart as if it had been prevented.

Authority schema v2 adds plans without rewriting the v1 tables. A transactional migration preserves existing identity, jobs and audit state. The v1 binary refuses the newer schema; automatic downgrade across this migration requires recovery rather than being advertised as compatible.

A protected executor receipt is committed before dispatch and deduplicates action IDs across interruption. Core records the authenticated receipt with independent selected inspection evidence in schema v3. Both resource locks remain held until a fresh new running incarnation is verified; executor verification performs another inspection before releasing its lock. Recovery reads receipts and never sends an effect request for an interrupted job. Missing or prepared receipts retain `needs_intervention`.

Session mutations recheck authentication inside the final authority transaction after inspection. Scoped task callers resolve their principal from a token bound to their kernel UID, task, scope, grant revision and core generation. Their protocol offers proposal and approved queueing, with no approval command. Duplicate queue requests recover the original job from durable state without contacting Engine. Schema v3 migrates v1/v2 transactionally and records receipt plus verification with the terminal job event.

Retention (PR-11, receipt schema v6): each receipt records its plan's expiry. Settled receipts (`verified`, `precondition_changed`, operator-`resolved`, and a stack's `partly_done`) beyond 1024 container and 256 stack receipts are pruned, oldest expiry first and at most 64 rows per insert, once their plan has been expired for an hour. A stack goes with all its member rows or not at all, so a batch stops before a stack that would take it past 64 rows; one whole stack (at most 17 rows) always fits, so a batch over budget always makes progress. Receipts that hold a lock (`prepared`, `effect_accepted`, `outcome_unknown`) are never pruned. A `resolved` row is pruned like other settled history (a resolved stack with its members): kept forever, every resolution would turn prunable history into a permanent row until the last-resort caps stop all execution. A core that crashed after the executor recorded `resolved` but before completing its own side retries `ResolveAction`, and gets the stored confirmation while the row is kept, or `no_longer_held` once it is pruned, after which it completes only past the plan's expiry and on a fresh measurement matching the approved evidence. A repeated action whose receipt was pruned is refused as `Expired` by its own plan, and its fresh precondition refuses it even after a clock step back. The 8192-row and 16 MiB caps remain only as last-resort stops.

Replay protection and its horizon: while a receipt is retained, its action id is bound to one plan digest. The same request returns the stored receipt without a second effect, and the same id with any other plan is `Conflict`. That binding lasts at least until the plan has been expired for `RECEIPT_RETAIN_AFTER_EXPIRY`, and for settled receipts only until retention needs the room; lock holders keep it indefinitely. The original plan itself cannot run again after pruning: it is `Expired`, and its precondition no longer holds. A new valid plan (fresh timestamps, its own digest) presented under a pruned id is unknown to the executor and executes as a fresh id would. That is not an escalation: the executor trusts core within the root-owned ceiling and does not verify approvals, so a caller able to send that request could equally mint a fresh id. Approval, single use and idempotency of a human request are core's, bound to the job id core generates. `a_pruned_action_id_with_a_new_valid_plan_executes_like_a_fresh_id` pins this behaviour.

A missing receipt after pruning (receipt schema v7): the receipt store keeps a prune watermark, the greatest plan `expires_at` among every receipt it ever pruned, raised in the same transaction as each prune and never lowered. Receipt lookups and `ResolveAction` carry the plan itself, exactly as core stored it; the executor recomputes its digest, refuses the request as invalid unless it equals the plan digest the request names (and, for `ResolveAction`, unless the plan is of the named kind and well formed), and judges by that plan's own `expires_at`, never a bare number. With no row the executor answers `never_recorded` when that expiry is strictly above the watermark (no receipt for the plan can have been pruned, so none was written and nothing was sent) and `no_longer_held` otherwise. Equality is `no_longer_held`. The answer reads no clock, so a clock step after a prune cannot turn an executed action into an unsent one. Rows that existed at the upgrade to schema 7 are `legacy` (schema 6 back-filled their expiry from the upgrade clock); a pruned legacy row leaves its action ID in `pruned_legacy`, which always answers `no_longer_held`. A store opened at schema 6 may have pruned without a watermark and starts at the maximum. Core releases a stack job as `precondition_changed` only on `never_recorded`, and only once its clock, read before the lookup was sent, is at least `EXPIRY_SETTLE_MARGIN` (5 s) past the plan's expiry: until then an `ExecuteStack` delivered earlier may not yet have reached the receipt store and could still prepare and run, so the job keeps its state and locks and the recovery poll asks again. This suffices because every execute path, container and stack, refuses the plan's own `expires_at` before it prepares and again after the durable Prepared row, immediately before the Engine call. On `no_longer_held` (or no answer) a stack or container job stays in (or moves to) `needs_intervention` with every lock and one `executor_receipt_missing` event; a never-recorded container job is held without that event, since a single container job is never released on absence. An operator resolution the executor answers with an absence completes on core's re-measured evidence, because no row holds an executor lock, but for either absence only under the same expiry guard: `no_longer_held` proves nothing about a delayed request either, and a store upgraded from schema 6 gives it even for a plan it never saw. Until then the request stays recorded and pending, the response tells the operator it waits for the plan to expire, and the retry loop completes it.
