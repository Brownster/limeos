# Container source descriptors before storage effects

Status: accepted for the next bounded RW-040 library slice, 2026-10-06. Installed qualification and effect integration remain open.

Docker's selected declarations identify intended sources. Lexical comparison cannot see ordinary symlinks or bind aliases, and a successful declaration read cannot establish that an unmount is safe. Resolve those sources in the storage executor's host mount namespace while retaining descriptors. This slice collects evidence; it adds no route, executor request, claim or storage effect.

Use the existing validated, bounded `ContainerStorageInventory` as the only input. Bind its full digest and five-second collection-start age. Require the host root mount identity before collection and at revalidation. For each declared source, use `openat2` with `O_PATH`, `RESOLVE_IN_ROOT`, `RESOLVE_NO_MAGICLINKS` and `RESOLVE_CACHED`. Ordinary symlinks can identify physical aliases. Magic links, missing paths, failed cached lookup and unsupported kernels fail the whole collection. Do not create a missing Docker source or fall back to blocking lookup. [Linux openat2 semantics](https://man7.org/linux/man-pages/man2/openat2.2.html).

Read only this process's retained descriptor names and mount IDs through bounded proc records. Match the mount ID to the complete bounded mount table before requesting inode metadata. Collect metadata only on an explicit set of local filesystems, using descriptor-relative `statx` without synchronization. Require the requested identity fields, a regular file or directory, and a live link. Record the resolved path, inode, device number and mount ID. Resolve both the declared and kernel-reported names again and require the same identity. [Linux statx semantics](https://man7.org/linux/man-pages/man2/statx.2.html).

Each directory source records its current mount plus every mount below its resolved path as a possible dependency. Preserve filesystem roots, mount points and device numbers so later binding can detect aliases and nested mounts. These are conservative host-view candidates; they do not prove which mounts a running container retained. Keep the complete mount-table digest and compare the table before returning and during revalidation. Retain descriptors until the evidence object is dropped. [Kernel mountinfo format](https://docs.kernel.org/filesystems/proc.html#proc-pid-mountinfo-information-about-mounts).

Bound lookup work by a two-second deadline, the existing 64-container/256-source ceilings, 512 aggregate mount references, a 1 MiB mount table and a 48 KiB serialized report. Refuse excessive output rather than truncating it. Cached resolution and the local-filesystem restriction reduce exposure to remote or userspace lookup stalls; the later service still needs bounded worker admission and a process deadline. Treat observations as fresh facts, never as a transaction against external Docker or mount operations.

The evidence object is constructed only by collection and owns its descriptors. Its serializable report is not authority. Revalidation must reject source replacement, rename, deletion, symlink retargeting, mount-table/namespace changes, expired Docker evidence and an expired work deadline. First-party unsafe code remains forbidden; reuse pinned rustix without new dependencies.

Tests exercise real unprivileged descriptor resolution for files, directories, ordinary links, missing/cyclic/magic links, changed paths and private temporary fixtures. Synthetic mount tables cover aliases, nested filesystems, component boundaries, mismatched kernel IDs, unsupported sources and aggregate/output limits. No production disk or Pi testing is required for this library slice.

Before mount or unmount execution, integration must additionally bind fresh UUID/topology evidence, inspect running-container mount namespaces, propagate pool/protection/share dependencies, reacquire Engine declarations, derive shared claims, enforce independent root ceilings and revalidate at effect time. Multi-device/virtual backing graphs remain unresolved here. A host path resolving to a block device number does not establish complete physical dependency coverage. DSK-001 and RT-001 remain open.
