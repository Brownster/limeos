# Smallest next RW-043 integration slice

Reviewed 2026-10-10 against the current P04 custody, staging and private-preparation docs and the existing domain, sole-writer job/approval store, schema-7 resource sets and schema-8 target-preparation integration. Source/design inspection only: no edits, tests, runtime/host commands or estimate based on agent time.

**Implement durable preparation-plan/approval/job binding first, plus a real restart integration test that rebuilds fresh private owners from custody.** Do not add a dispatcher, executor RPC, service, public archive upload or live restore operation in this slice. This delivers working durable Store APIs and proves the join between existing libraries and SQLite; it does not turn library prerequisites into installed restore capability.

## Concrete boundary

The trusted integrator obtains a genuine `RetainedArchive`, calls its existing `stage`, then calls `preparation::plan` with the exact genuine manifest and its own current selection/limits. Persist the returned custody binding and preparation-plan identity, not a serialized owner or private attempt path. A new closed `BackupPreparationJobPlan` should also bind action/job ID, principal/grant revision, creation/expiry, ordered selected resource IDs and a trusted private-workspace/policy identity. The caller derives all of these from trusted configuration and genuine owners; no API accepts an archive pathname, destination override, metadata override or claim list.

Keep three identities distinct: the custody binding's exact archive/policy/manifest identities; `PreparationPlan::identity()` over full manifest/selection/limits; and the existing approval digest over the complete persisted job plan. Do not substitute revision equality, an archive digest alone or a prepared-record digest for any of them.

Persistence currently may depend only on domain/identity/policy; backup-archive may depend on domain. Keep that architecture. Promote only the six-field closed, pure custody binding into the domain and re-export it at the existing `custody::CustodyBinding` path, preserving encoding and public compatibility. Its validation is pure. Keep `RetainedArchive`, `VerifiedCatalog`, `PreparationPlan`, `PreparedRestore`, descriptors and filesystem work in backup-archive. The job plan needs only bounded binding facts and identities, so it does not require exposing every admission/preparation type through the API schema or adding an adapter dependency to persistence.

Use the current `StorageManage` authorization and human approval machinery: administrator plus explicit current grant, digest-bound random approval token stored hashed, then atomic one-time approval consumption + job + required resource set + audit event. Add an explicit `Intent::BackupPreparePrivate` rather than using HealthProbe or a storage-target intent. The generic queue path must continue rejecting this operation; only its dedicated approved queue method inserts it. Existing container/storage candidate queries must continue excluding it, so a queued binding never dispatches accidentally.

The smallest resource scope is private preparation, not live destinations: conservatively serialize private preparations on a fixed `backup:preparation` primary resource; additionally bind `backup:custody:<record_id>` and the existing `storage:configuration` interlock. Derive this complete set in the same queue transaction and rederive/compare it at startup. No caller supplies claims. This is a deliberately coarse logical set for this non-dispatched slice; it neither reserves disk space nor proves physical backing/alias conflicts, writer exclusion or eventual live destination claims. A later executor cannot rely on it until its actual protected roots/backing dependencies and complete write scope are qualified. Do not lock a guessed path or fabricate mount/UUID evidence to make that later step appear complete.

No new Running claim or terminal-result implementation is needed now. Reuse the existing schema-7 acquisition/retention invariants for any future dispatch. Unknown/intervention ownership, revocation and expiry must never authorize automatic release. Generic transitions must remain unable to dispatch or complete the new closed intent. Cancellation in this slice affects only an unconsumed plan or a still-queued job; it does not delete custody or private orphans.

## Durable behavior to implement

Mirror `Store::{plan,approve,replay,queue,cancel}_storage_targets`, with a bounded operation-specific plan table and a dedicated typed job getter. Bound plan bytes/counts before allocation or SQL writes and choose the existing plan TTL rather than a new token scheme. Reading a consumed plan and replaying the same principal/key/plan/approval returns the same job after expiry and after restart. Changed bytes under that key, another principal or another approval conflicts. Approval rotation cannot resurrect a consumed plan. Replay is a pure DB read: no archive scan, read, refresh, staging, new owner or new audit event.

The custody publication precedes the DB transaction: a crash before the durable job binding leaves an inert custody orphan. There is no cross-filesystem/SQLite atomic transaction; do not add directory scanning/adoption to hide that gap. A committed job binds the exact retained record, but recovery still uses `custody::recover` with the current full admission policy and finite limits, re-admitting actual bytes. It then stages a fresh catalog and derives a fresh plan from current trusted selection/limits. Only an identical preparation-plan identity permits fresh private preparation. Changed policy, roots, UID/GID/modes, resource ordering, limits, missing or changed archive bytes refuse. No old catalog, prepared JSON, success marker or pathname can reconstruct an opaque owner.

After a recovery test creates a fresh `PreparedRestore`, verify its checked readers and call explicit discard. Do not mark the durable job Succeeded merely because a process held a prepared owner: the current library publishes no recoverable prepared artifact/receipt, so an installed completion claim would outlive its authority. Prepared results, promotion/reconciliation and worker receipts are a later slice.

## Meaningful acceptance tests

- Real custody publication followed by a failing DB/audit commit creates no job/consumed approval; the retained object remains an orphan and is never found by a directory scan. The caller may retain its known binding for explicit cleanup; do not fabricate a recovery job.
- Queue commit, lost response and real process death: reopening returns the same job/intent/binding/resources/consumed approval without duplication or new dispatch. The test must use real custody bytes and SQLite commits, not fixtures that import an opaque owner from JSON.
- Same-key altered custody binding, preparation identity, selected resources, principal/revision/workspace policy, approval or deadline conflicts; unknown/duplicate/oversized fields and count arithmetic refuse before state changes.
- Authorization/CSRF at any future caller boundary and Store grant checks remain current; household/operator cannot gain restore/storage power. Expiry/revocation blocks new approval/queue while exact consumed replay remains a read.
- Recover the exact durable binding in a fresh process, stage and plan afresh, compare identity and prepare privately; checked bytes match. Mutate archive/record/policy/target metadata/limits/order and prove fresh recovery/preparation refuses while durable identity remains unchanged. A pure idempotent replay must not touch the mutated archive at all.
- SIGKILL before custody publication, between publication and DB commit, after DB commit and during fresh staging/preparation preserves the correct orphan/queued/ephemeral distinction. No old attempt is adopted; no live destination is opened. Use existing library kill fixtures where applicable, not a second decoder.
- Migration from actual schema 8 preserves every old intent/approval/receipt/claim byte. Inject migration/audit failure and prove rollback, unchanged generation and no recovery event. Corrupt queued binding/digest/required set/approval link or compiled guard: startup refuses instead of repairing it.
- Confirm no new operation appears in existing dispatcher candidates, and generic transition/queue methods cannot run or complete it. Route tests should be added only when a route exists; this slice creates none.

Run focused domain/persistence/cross-library tests and required repository/contract/Rust gates for this change, preserving meaningful failure attempts. Installed guest qualification is separate; synthetic limits never become production defaults.
