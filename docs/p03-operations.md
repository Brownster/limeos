# Approved container lifecycle operations

P03's restart, start, stop and bounded log paths are available only on a disposable test host. Wybie continues to run the frozen Python application. The Compose plan foundation remains phase work.

The standard package installs with every effect disabled and an empty `managed_containers` list in `/etc/limeos/system-policy/container.json`. On the test host, an operator may enable `allow_restart`, `allow_start` or `allow_stop` separately and list the full 64-character IDs of the containers LimeOS may manage. `allow_container_logs` separately permits bounded reads for those managed IDs. Omitted new flags default to false. Preserve the package's `core_uid` and inventory read capabilities. Validate with `limeosctl check-ceiling /etc/limeos/system-policy/container.json CORE_UID`, then restart only `limeos-containerd`. Core and the assistant cannot edit this root-owned policy or open Docker's socket.

The shadow unit always includes the `read-only` argument and refuses a write-enabled ceiling at startup. Its accounts, sockets and receipt state use the separate `limeos-shadow` prefix. It must never be used for write qualification on the reference host.

Select **Start**, **Stop** or **Restart** in the container list. Start requires a stopped container; stop and restart require a running container. The preview binds the action, full container ID, image, running state and last start time and expires after five minutes. The explicit approval button issues a one-use human approval and queues the durable job. Task callers can propose or submit an already approved plan; they cannot approve it themselves. The current grant is checked again before dispatch, and the executor independently checks its action ceiling, allowlist and the resource's fresh identity.

Recent operations survive browser reload. Progress comes from stored, owner-scoped job events. A queued operation can be canceled. In-flight cancellation returns a conflict, because the host effect may already have begun. An interrupted queue response can be retried with its original approval, plan and request key; it returns the existing job without another Engine call. All lifecycle operations share the selected container's resource lock.

`succeeded` requires an accepted Engine response and a further executor inspection. Start and restart must produce a later running incarnation of the same container/image; stop must leave the selected incarnation stopped. `needs_intervention` retains the resource lock. Missing, prepared or ambiguous receipts never authorize replay. Inspect the job, executor journal and protected receipt before making a recovery decision. There is no automatic unlock command in this slice. Never delete the receipt database or reset job state to queued to retry an uncertain operation.

Core authority schema v4 stores receipts and verification in `/var/lib/limeos/core/core.sqlite`; executor receipt schema v3 lives in `/var/lib/limeos/executors/container/receipts.sqlite`. These are separate private stores. Migration preserves existing restart plan digests, approvals and receipt barriers. Older binaries refuse newer authority/receipt schemas; package downgrade alone is not a supported recovery across the migration.

**Logs** reads the last 100 lines; the API accepts 1–200. Reads never follow the stream, have a four-second deadline and return at most 24 KiB of text. Terminal controls and common credential-bearing lines are filtered before display. This filter recognizes common patterns; it cannot identify every possible application secret. Log access requires the current container-management grant, its specific resource scope and the executor's log ceiling. A viewer's inventory grant does not permit logs. Logs are not saved in authority events. The log dialog renders escaped text and refreshes only on request.

The Engine adapter follows Docker's [versioned API](https://docs.docker.com/reference/api/engine/) and [restart contract](https://docs.docker.com/reference/api/engine/version/v1.40/#operation/ContainerRestart), negotiates a supported API, uses fixed selected inspection and restart endpoints, bounds response size/time and never retries a POST after losing its response.

Run local Rust checks with the pinned toolchain and `cargo test --workspace --locked`. The isolated browser fixture is `uv run tests/frontend/restart.py` after building the UI; it expects Google Chrome at `/usr/bin/google-chrome`. For real Engine qualification, build a trusted source/toolchain bundle with `uv run tests/privileged_vm/build_bundle.py --output /tmp/limeos-p03-lifecycle-build.tar.gz`, then use the existing VM runner with `--guest-script tests/privileged_vm/p03_lifecycle_guest.py --build-bundle /tmp/limeos-p03-lifecycle-build.tar.gz --build-output dist/p03-lifecycle-debian`. Supplying the previously qualified 0.3.0 repository with `--repository dist/p03-debian/limeos-repo --retain-previous-repository` additionally tests a genuine schema upgrade; rebuilding both package versions from current source does not prove this migration. The runner requires KVM, uses a verified Debian image and destroys its own VM afterward. The test-only signing key is generated inside that VM and is never a release key.
