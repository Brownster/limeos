# Approved container lifecycle operations

P03's restart, start, stop and bounded log paths are available only on a disposable test host. Wybie continues to run the frozen Python application. The Compose plan foundation remains phase work.

The standard package installs with every effect disabled and an empty `managed_containers` list in `/etc/limeos/system-policy/container.json`. On the test host, an operator may enable `allow_restart`, `allow_start` or `allow_stop` separately and list the full 64-character IDs of the containers LimeOS may manage. `allow_container_logs` separately permits bounded reads for those managed IDs. Omitted new flags default to false. Preserve the package's `core_uid` and inventory read capabilities. Validate with `limeosctl check-ceiling /etc/limeos/system-policy/container.json CORE_UID`, then restart only `limeos-containerd`. Core and the assistant cannot edit this root-owned policy or open Docker's socket.

The shadow unit always includes the `read-only` argument and refuses a write-enabled ceiling at startup. Its accounts, sockets and receipt state use the separate `limeos-shadow` prefix. It must never be used for write qualification on the reference host.

Select **Start**, **Stop** or **Restart** in the container list. Start requires a stopped container; stop and restart require a running container. The preview binds the action, full container ID, image, running state and last start time and expires after five minutes. The explicit approval button issues a one-use human approval and queues the durable job. Task callers can propose or submit an already approved plan; they cannot approve it themselves. The current grant is checked again before dispatch, and the executor independently checks its action ceiling, allowlist and the resource's fresh identity.

Recent operations survive browser reload. Progress comes from stored, owner-scoped job events. A queued operation can be canceled. In-flight cancellation returns a conflict, because the host effect may already have begun. An interrupted queue response can be retried with its original approval, plan and request key; it returns the existing job without another Engine call. All lifecycle operations share the selected container's resource lock.

`succeeded` requires an accepted Engine response and a further executor inspection. Start and restart must produce a later running incarnation of the same container/image; stop must leave the selected incarnation stopped. `needs_intervention` retains the resource lock. Missing, prepared or ambiguous receipts never authorize replay. Inspect the job, executor journal and protected receipt before making a recovery decision. There is no automatic unlock command in this slice. Never delete the receipt database or reset job state to queued to retry an uncertain operation.

Restoring the core database from a backup is outside what the receipts can protect. The executor's receipt store proves whether an action ran, and core notices a receipt store that was lost, recreated or restored (its per-open epoch changes) for every job core was holding at the time. A core database rolled back to a moment when a job was still `queued` holds no trace that the job was later dispatched; if the receipt store is lost or replaced as well, nothing remains to stop that job from being dispatched again. So after restoring `core.sqlite` from an older copy, keep container control disabled (or the container executor stopped), list the jobs the restored database shows as `queued` or `running`, compare each with the executor journal and the containers' actual state, and cancel or resolve them before enabling effects again. Restore both stores from the same moment when possible, and never restore one of them alone to retry an operation.

Core authority schema (`SCHEMA_VERSION` in `crates/persistence/src/lib.rs`, v4 when this slice shipped) stores receipts and verification in `/var/lib/limeos/core/core.sqlite`; executor receipt schema v8 (`RECEIPT_SCHEMA_VERSION` in `crates/executor-container/src/lib.rs`; v3 when this slice shipped) lives in `/var/lib/limeos/executors/container/receipts.sqlite`. These are separate private stores. Migration preserves existing restart plan digests, approvals and receipt barriers. Older binaries refuse newer authority/receipt schemas; package downgrade alone is not a supported recovery across the migration.

**Before a core schema upgrade** core keeps a snapshot of the store beside it, named after the version it upgrades from: `/var/lib/limeos/core/core.sqlite.v16.snapshot` for an upgrade from schema 16, with a small record of what it was taken from and what it is, `core.sqlite.v16.snapshot.state`. The snapshot is taken through SQLite (`VACUUM INTO`), so it holds everything committed, including what was still in the WAL; it is synced, checked and only then renamed into place, with the store's mode (0600) and owner. A new store gets none, and a store already at the current schema takes none. The upgrade runs on a connection that holds the store exclusively from before the snapshot until the migrated store is committed, so no other program can read or write it meanwhile; one that has the store open makes the upgrade wait half a second and then fail, and core retries at its next start.

If an upgrade fails after its snapshot (core then refuses to start and systemd starts it again every few seconds), each later attempt keeps that snapshot instead of writing another, as long as the store and the snapshot are exactly what the record describes: the snapshot's length, inode and modification time and the store's length are compared first, and only if they match are the store and then the snapshot read and hashed. Any doubt (no record, an unreadable one, a commit since) means the snapshot is taken again. If core wrote a snapshot but could not write its record, the log says so: the next attempt cannot keep that snapshot and writes another.

Before SQLite opens the store, core removes what an interrupted snapshot left (`core.sqlite.v*.snapshot.partial`, `.snapshot.partial-journal`, `.snapshot.state.partial`); something under one of those names that cannot be removed (a directory, say) is left alone and matters only to an upgrade that needs that exact name, which then refuses. The store's other snapshot files count towards free space by what removing them gives back (their allocated blocks, and nothing for a file another hard link still names). If the free space alone fits the new snapshot with the 8 MiB reserve to spare, it is written first and the older files are removed after it, even when the migration itself then needs their space; only if the snapshot itself does not fit are they removed (and the directory synced) first. Either way the store is unchanged until the new snapshot is in place, and an older version's snapshot could only roll back across an upgrade the store has already completed. The space needed is the new snapshot plus the upgrade's own writes: the schema-17 event indexes, estimated from the rows they cover, and the schema-19 rewrite of `jobs`, bounded by three pages for every page of that table (each page and its split sibling in the WAL, the sibling again in the database file), plus startup recovery's records, bounded by the depth of the trees they go into. Retention's emergency pruning, which runs only when even the audit reserve cannot hold the recovery records, is not counted. If removing a file fails, or the new snapshot and those writes would not leave the 8 MiB write reserve free, core refuses to start, removes and writes nothing, and the store stays at its old schema; for lack of space, whether found before the upgrade or by running out during it, the log names the bytes needed and available. After a successful start there is one snapshot and its record, about the size of the store's pages in use (free pages are left out). Delete them once the upgraded build has run long enough to trust; core never needs them.

If core refuses a store because one of its tables, indexes or triggers differs from what this build creates, the log names it (for example ``the store's table `jobs` does not match this build's schema``). Core changed nothing. The store was changed outside LimeOS or written by another build: install the build that wrote it, or restore `core.sqlite` from a backup or a pre-upgrade snapshot as below.

To go back to the build before an upgrade, no container effect may run between the first start on the restored store and the end of its reconciliation. Installing a package restarts `limeos-storaged`, `limeos-containerd` and `limeos-core` from its `postinst` (every `postinst` in the repository's history does), so stopping or masking a unit does not survive it (a masked unit makes the installation fail); the container executor's ceiling does, because the installation validates and keeps it and the restarted executor reads it. Storage effects are not governed by that ceiling: the storage target and mount units are stopped by the package's `prerm` and never started by `postinst`, so leave them stopped. With every container effect flag off the executor refuses all effects and also does not open its receipt store, so it cannot resolve a held job either: held jobs are resolved only after the flags are back. Core never dispatches a held job: a job in `needs_intervention` (or `running`, `verifying`, `outcome_unknown`) is only looked up by receipt, never executed again (`dispatch_one` in `bins/core/src/operations.rs`: an execute is sent only for a `queued` job, or for a claim this same process made before losing the answer). The procedure works only when both packages use the same executor receipt schema (`RECEIPT_SCHEMA_VERSION`): the older executor refuses a newer receipt store once the flags are back, and the receipt store must never be rolled back alone.

1. In `/etc/limeos/system-policy/container.json` set `allow_restart`, `allow_start`, `allow_stop` and `allow_stack` to `false`, validate with `limeosctl check-ceiling /etc/limeos/system-policy/container.json CORE_UID`, and run `systemctl restart limeos-containerd`.
2. `systemctl stop limeos-core`, then move `core.sqlite`, `core.sqlite-wal` and `core.sqlite-shm` in `/var/lib/limeos/core` aside (keep them until the restore is confirmed).
3. `install -o limeos-core -g limeos-rpc -m 0600 /var/lib/limeos/core/core.sqlite.v16.snapshot /var/lib/limeos/core/core.sqlite` (core runs as `limeos-core` with group `limeos-rpc`; a copy owned by root cannot be opened by core and is refused).
4. Install the older package. Its configuration step starts core on the restored store; any dispatch it attempts is refused by the executor.
5. Make sure no restored job is still `queued` (the only jobs a dispatcher sends). There is no supported command that lists or cancels every queued job across users: the web interface lists only a user's own latest 32 container jobs (and stack jobs likewise) and cancels only the user's own. What does protect them is the plan's expiry: a queued container or stack job is sent only while its approved plan is unexpired (five minutes after it was created); an expired one is closed as `precondition_changed` at the next dispatcher pass, before anything is sent (`dispatch_one` and `dispatch_stack`). So wait until at least five minutes (by the host's clock) have passed since the snapshot's modification time (`stat -c %y core.sqlite.v16.snapshot`), which is no later than the start of the upgrade; every job queued in the snapshot then has an expired plan. Then list what is left, read-only, with core stopped or on a copy: `python3 -c "import sqlite3; c=sqlite3.connect('file:/var/lib/limeos/core/core.sqlite?mode=ro', uri=True); print(c.execute(\"SELECT id,principal,state,json_extract(intent,'$.operation') FROM jobs WHERE state IN ('queued','running','verifying')\").fetchall())"` (as root). Container and stack jobs should no longer be `queued`; if one is, or if the host's clock cannot be trusted, cancel it as its owner in the web interface (`POST /api/v1/container/jobs/{id}/cancel`, or the stack equivalent), and do not restore the flags until none is. Compare the held jobs (`needs_intervention` and the other uncertain states) with the executor journal and the containers' actual state, but do not resolve them yet: with the flags off a resolution is refused (as a retryable or a final refusal, depending on the build), and nothing has changed.
6. The restored store is the store as it was at the start of the upgrade, so everything recorded after it is undone, not only jobs: sessions and task tokens revoked since are valid again, password changes and grant removals are reverted, and users created since are gone. Re-apply those before anyone else reaches the web interface.
7. Restore the effect flags in `container.json`, validate it and run `systemctl restart limeos-containerd` (it now opens its receipt store; if the receipt schemas differ it refuses to start here, and the flags must go back off).
8. Resolve the held jobs from what step 5 found. Held jobs are not dispatched while you do.

Starting the newer build on the restored store upgrades it again (and takes a new snapshot).

**Logs** reads the last 100 lines; the API accepts 1–200. Reads never follow the stream, have a four-second deadline and return at most 24 KiB of text. Terminal controls are stripped and credential-bearing lines are replaced by a marker before display. A line that names a credential word (password, secret, token, cookie, session, authorization and the like) is replaced unless only plain lower-case prose follows the word, so some harmless lines are hidden too; lines holding a known secret shape (bearer tokens, JWTs, cloud and service keys, URL userinfo) and private key blocks are always replaced. The filter cannot identify every application secret: one given as bare lower-case words after its name, or before it, or on a line that never names it is still shown. Log access requires the current container-management grant, its specific resource scope and the executor's log ceiling. A viewer's inventory grant does not permit logs. Logs are not saved in authority events. The log dialog renders escaped text and refreshes only on request.

The Engine adapter follows Docker's [versioned API](https://docs.docker.com/reference/api/engine/) and [restart contract](https://docs.docker.com/reference/api/engine/version/v1.40/#operation/ContainerRestart), negotiates a supported API, uses fixed selected inspection and restart endpoints, bounds response size/time and never retries a POST after losing its response.

The isolated browser fixture is `uv run tests/frontend/restart.py` after building the UI; it expects Google Chrome at `/usr/bin/google-chrome`. For real Engine qualification, build a trusted source/toolchain bundle with `uv run tests/privileged_vm/build_bundle.py --output /tmp/limeos-p03-lifecycle-build.tar.gz`, then use the existing VM runner with `--guest-script tests/privileged_vm/p03_lifecycle_guest.py --build-bundle /tmp/limeos-p03-lifecycle-build.tar.gz --build-output dist/p03-lifecycle-debian`. The runner requires KVM, uses a verified Debian image and destroys its own VM afterward. The test-only signing key is generated inside that VM and is never a release key.

**Whole-stack start, stop and restart** use the same preview, human approval, durable job and receipt path for a registered Compose project whose catalog and Engine samples are fresh and show no inventory issue. They act only on ordinary (non one-off) service containers by exact ID, one at a time in ID order: start on stopped members, stop and restart on running members. They never run `docker compose`, write Compose files, create or remove containers, or order by `depends_on`. A failure stops the run; later containers are recorded as not attempted and the job is `needs_intervention` with per-container outcomes. The stack and every member share locks with single-container jobs. The ceiling adds `"allow_stack": true` and `"managed_stacks": ["project"]` (default off); every target must also be in `managed_containers` and its own `allow_*` flag must be set. Executor receipt schema v4 adds the stack table; older binaries refuse it. The shadow profile refuses `allow_stack`. See `docs/plans/2026-11-05-stack-lifecycle-design.md`.
